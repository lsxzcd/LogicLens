# 队友分工方案（Task Allocation）

> 编写时间：管线已打通、CI 全绿、提交物框架完成，**正式数据待实验室机器产出**。
> 结论：**现在应该分工**，因为可并行的工作已经明确，而且三条主线代码边界互不重叠。

---

## 一、先回答：为什么现在该分工

### 1.1 支持分工的理由

| 理由 | 说明 |
|---|---|
| **瓶颈已明确** | 唯一阻塞是"实验室机器 + 模型选型"，其余工作**都可并行** |
| **边界已经划好** | `agent/`、`skill/`、`experiments/data/`、`serve/` 互不重叠，且有 CI 守卫 |
| **增量收益递减** | 单人继续做，边际产出在下降；而有三块独立工作面闲置 |
| **赛题明确考"工程质量"（20 分）** | 协作规范、评审流程本身就是评分点 |
| **时间风险** | 全量评测预计 7~37 小时，越晚开始越好不了 |

### 1.2 但有一条**前置纪律**

**当前代码处于"可用但未验证于目标硬件"的状态。** 因此：

- ✅ 可以并行开发**不依赖显卡**的部分
- ❌ **不要**在拿到实验室机器的真实数据前，写死任何性能结论
- ⚠️ **不要**同时改 `agent/controller.py` 与 `vivado/run_flow.tcl`——这两个文件决定判定口径，并行改会冲突

### 角色 A：数据集与技能包

**目标**：让评测集更全面，让技能包从"5 道题的 6 张卡"扩到"全量数据支撑的完整技能库"。

#### A1. 扩充评测数据集（独立性强，可立即开始）

- [ ] 用 `tools/fetch_verilogeval_problem.py` 导出**全部 156 道题**
- [ ] 按题型分类统计：组合逻辑 / 时序 / FSM / 向量操作 / 边界条件
- [ ] 挑 **20~30 道代表性题目**跑一轮，记录失败分布（需模型服务）
- [ ] 产出：`experiments/data/analysis/` 下的分类统计

**交付物**：数据集分类报告 + 失败分布数据
**边界**：只加 `experiments/data/` 下文件，**不改 `agent/`**

#### A2. 扩充技能包（核心交付）

- [ ] 阅读 `skill/skill_cards.json` 了解现有 6 张卡的格式
- [ ] 从 A1 的真实失败中提炼新技能卡，**每张必须有**：
  - 来源失败（具体到题目和现象）
  - 观测证据（日志片段、MD5 对比等）
  - 修复方法（提示词规则 / 可执行检查）
  - **验证题数与有效性结论**（赛题硬性要求）
- [ ] 对能用结构检查表达的规则，在 `agent/rtl_lint.py` 加检查（**注意：这个文件归 B，改前先沟通**）

**交付物**：技能卡 10+ 张
**验收标准**：每张卡有实测效果，且**至少一张记录"无效"或"部分有效"**（全有效的技能包不可信）

#### A3. 自建题集补充

- [ ] 为 `experiments/dataset_smoke` 增加几道题（覆盖时钟/复位/位宽边界）
- [ ] 每道题配 sidecar testbench，使 `tools/check_dataset.py` 通过

---

### 角色 B：智能体质量

**目标**：提升通过率，尤其是赛题最看重的**"可综合"末级通过率**。

#### B1. 实现模型兜底解析（已识别的缺口）

当前 `parse_task_with_model` 是**占位实现**。当规则解析不确定时（例如题面没给模块名、端口描述模糊），应让模型兜底。

- [ ] 实现 `parse_task_with_model`：仅在规则解析**不确定**时调用模型
- [ ] 关键：模型返回**必须是结构化输出**（JSON），不能是自由文本
- [ ] 加测试：规则能解析时**不得**调用模型（省墙钟）
- [ ] 加测试：模型返回非法 JSON 时优雅回退到规则结果

**边界**：改 `agent/task_parser.py`
**风险**：中等——这是评测主路径，必须带测试

#### B2. 多候选生成与打分（已识别的缺口）

当前是**单候选串行重试**。赛题的 `pass@5` 需要 5 次独立采样，而多候选可以提高单次成功概率。

- [ ] 为每道题生成 N 个候选（N 可配置）
- [ ] 用现有 `agent/candidate_ranker.py::score_result` 打分排序
- [ ] **重要**：结构检查（`rtl_lint`）作为**预筛**，把有明显缺陷的候选排后
- [ ] 记录候选数量与选择结果，便于事后分析

**边界**：改 `agent/controller.py`（**与判定口径相邻，改前先沟通**）
**风险**：高——直接影响墙钟和通过率，必须先小规模验证

#### B3. 结构检查器扩充（配合 A2）

- [ ] 现有 4 条规则：`combinational_uses_edge`、`edge_on_non_clock_signal`、`undeclared_clock_signal`、`identity_expression`
- [ ] 可扩充：latch 推断、多驱动、位宽截断、复位极性
- [ ] **每条新规则必须有测试**，且用**真实失败案例**做正例、**正确实现**做反例

**边界**：改 `agent/rtl_lint.py`
**注意**：新规则的 findings **不得覆盖工具判定**（官方 testbench 才是权威）

### 角色 C：部署与容器

**目标**：让提交物在目标环境真的能跑；产出 `MODEL.md` 的实测数据。

#### C1. 实验室机器环境勘察（**最高优先级**）

连上实验室 Linux 虚拟机（UU 远程 `201997749`）后：

- [ ] `rocminfo` / `rocm-smi` 看显卡型号与显存
- [ ] 确认 ROCm 版本是否满足（需 v7/HIP7；RDNA2 可能要 Vulkan 回退）
- [ ] 确认 Vivado / Vitis 是否已装、版本、能否找到 `xczu3eg-sbva484-1-e`
- [ ] 确认是否有 Docker
- [ ] **产出**：一份环境事实清单

**交付物**：环境勘察报告，**这是决定模型选型的唯一依据**

#### C2. 验证 `serve/` 与容器（本机做不到的）

- [ ] 在 Linux 上跑 `serve/fetch-model.sh`、`serve/start.sh`
- [ ] 跑 `serve/record_service.py`，**记录真实 `size_vram`**（本机是 0，无参考价值）
- [ ] 构建 `Dockerfile` 验证镜像可构建
- [ ] **用 `--network none` 验证断网可用**（赛题硬要求）
- [ ] 把发现的问题回报，修正脚本

**交付物**：`MODEL.md` 的实测字段 + 容器验证结论

#### C3. 模型选型与实测

- [ ] 按显存约束（**单卡 32 GB，不允许跨卡**）筛选候选模型
- [ ] 实测 2~3 个候选的：`size_vram`、生成速度、VerilogEval 前 10 题通过率
- [ ] 选定主模型，**记录仓库地址 + 版本/摘要 + 量化方式**
- [ ] 填入 `model/MODEL.md` §4

**交付物**：模型选型报告 + `MODEL.md` 定稿

## 四、协作纪律（避免互相踩踏）

### 4.1 文件归属表（**改前先看这张表**）

| 文件/目录 | 归属 | 说明 |
|---|---|---|
| `experiments/data/` | A | 只加文件，不改代码 |
| `skill/skill_cards.json` | A | 技能卡的唯一来源 |
| `agent/task_parser.py` | B | |
| `agent/rtl_lint.py` | B（A 可提需求） | 规则要有测试 |
| `agent/controller.py` | B | ⚠️ **同时只允许一人改** |
| `vivado/run_flow.tcl` | **D 独占** | ⚠️ 判定口径，改语义必须同步字段表 |
| `agent/testbench.py` | B | ⚠️ 单一接口，改动影响全员 |
| `serve/`、`Dockerfile*` | C | |
| `model/MODEL.md` | C | |
| `REPORT.md`、`docs/` | D | 其他人可提 PR |

### 4.2 三条硬性约定

1. **推代码前用干净克隆跑测试**——这是唯一能发现"依赖了未提交文件"的方法（该缺陷已真实导致 CI 全挂一次）
2. **不要把本机路径、模型权重、`experiments/runs/` 提进仓库**
3. **不要用 `--mock` 数据写报告结论**

### 4.3 PR 流程

```bash
git checkout -b <方向>/<简述>        # 如 feat/parse-model-fallback
# ... 开发 ...
python3 -m unittest discover -s tests
git push -u origin <分支名>
# 然后在 GitHub 开 PR，等 3 个检查通过后合并
```

## 五、优先级与时间建议

| 优先级 | 任务 | 理由 |
|---|---|---|
| **P0** | C1 环境勘察 | **阻塞其他一切**——不知道显卡就定不了模型 |
| **P0** | A1 数据集扩充 | 独立、可立即开始、为 A2 提供原料 |
| **P1** | C2 容器验证 | 提交物硬要求，且能消掉报告中多条"未验证" |
| **P1** | B1 模型兜底解析 | 已识别的功能缺口 |
| **P2** | A2 技能包扩充 | 依赖 A1 的失败数据 |
| **P2** | B3 结构检查扩充 | 可与 A2 配合 |
| **P3** | B2 多候选生成 | 风险高，应在评测流程稳定后再做 |

**建议的第一周安排**：

- 队友 A：A1 → A2 起步（不需要显卡）
- 队友 B：B1 → B3（不需要显卡）
- 队友 C：等实验室机器可访问 → C1 → C2 → C3
- 你：D + 协调，同时推进 C1 的访问（这是所有人的阻塞点）

## 六、验收标准（怎么算"做完了"）

| 交付物 | 验收标准 |
|---|---|
| 技能卡扩充 | 10+ 张卡；**至少 1 张记录"无效"或"部分有效"**；每张有验证题数与实测效果 |
| 模型兜底解析 | 规则可解析时**不调用模型**（有测试证明）；非法输出能优雅回退 |
| 环境勘察 | 显卡型号、显存、ROCm 版本、Docker 可用性、Vivado 版本，**都有命令输出为证** |
| 容器验证 | `--network none` 下能完成读题到出码；有日志为证 |
| `MODEL.md` | `size_vram > 0` 且 < 32 GB；有 `record_service.py` 输出为证 |
| 全量评测 | `REPORT.md` 第 7 节有真实数字；**基线与智能体配置一致性检查通过** |

## 七、一句话总结

**可以分工，而且该分了。** 三条主线（数据/技能、智能体、部署）边界清晰、互不冲突；
**唯一的阻塞点是实验室机器的环境勘察**，那件事优先做，其余都可立即并行。
